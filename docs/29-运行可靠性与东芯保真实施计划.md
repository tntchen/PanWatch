## 2. 实施顺序与门禁

### R1 · Tushare 镜像依赖修复

**目标**：让 NAS 容器不再因 Python 包缺失而拒绝 Tushare K 线请求。

**拟改动**：

- 在 `requirements.txt` 加入有下限且可复现的 `tushare` 依赖；同步修正 vendor/docstring 的“软依赖”描述。
- 补充镜像/运行时回归用例：vendor 成功 import；token 缺失仍输出明确、非崩溃的配置错误；Docker 构建继续由 CI 覆盖。
- 发布一个新版本（建议 `0.4.4`）并在 NAS 以固定 tag 部署；由管理员在数据源页填写 token，单源测试 `600519` 与 `688110`。

**非范围**：不把 token 写入仓库、镜像或日志；不扩展 Tushare 的基本面/资金流/龙虎榜接口；不自动启用该源。

**验收**：NAS 容器 `import tushare` 成功；数据源页不再出现“未安装”；正确 token 下两个样本有日线返回，缺 token 时给出准确配置提示。

**决策 D29-1**：✅ 已确认（2026-07-27）。Tushare 从“开发机软依赖”升级为“应用镜像必装依赖”。

### R2 · 数据源健康、降级与数据时效

**目标**：在不把偶发失败误当永久故障的前提下，让系统有可解释、可控的自动备源能力。

**拟改动**：

1. 扩充现有内存指标，使用 `(datatype, vendor, market)` 键，而非只按 vendor 汇总；增加 p95、最后尝试时间、连续运输/服务失败数、错误类别和熔断状态。
2. 给 `Engine` 加熔断门：连续可归因的网络/服务异常达到阈值后跳过该源，冷却期后只做一次恢复探测；已有顺序备源立即承接。
3. `empty`（例如非交易日无 K 线）保留为观测指标，但**不得**触发熔断；token 缺失/鉴权失败单列为“配置异常”，不与网络异常混淆。
4. 在数据源页展示健康状态和降级原因；在分析/简报原始数据中写入实际 vendor、采集时间、是否备源及数据时效。
5. 对交易型简报增加数据闸门：关键行情/K 线超过时效或所有备源失败时，记录原因并抑制交易建议通知；资讯类可以标注降级后发送。
6. 添加单元和 API 回归：主源异常→备源成功、熔断→冷却探测、空数据不熔断、token 错误分类、健康状态隔离、关键简报抑制。

**初始阈值（可配置、先保守）**：同键 3 次连续运输/服务失败熔断 5 分钟；恢复探测一次成功即闭合；阈值和时长不写死在业务逻辑中。

**验收**：模拟超时后在单次调用内切备源；熔断期间不继续消耗故障源；UI/日志可定位数据类型、市场、实际来源和最近成功时间；东财保持人工禁用；至少一周生产指标无异常抖动。

**决策 D29-2**：✅ 已确认（2026-07-27）：交易简报关键数据失效时直接抑制推送并落失败记录。

#### R2 执行记录（2026-07-28，已由所有者审计确认）

- `packages/marketdata/src/marketdata/defaults.py`：健康状态由仅 provider 聚合改为 `(datatype, vendor, market)` 隔离；保留旧 `snapshot()` 兼容输出。新增最后尝试时间、连续失败数、熔断状态与恢复时间。
- `packages/marketdata/src/marketdata/engine.py`：连续 3 次异常后熔断 5 分钟，期间跳过主源并继续顺序备源；冷却到期的下一次调用即恢复探测。`empty` 不参与熔断，避免非交易日误伤。
- `packages/marketdata/src/marketdata/client.py` + `src/web/api/datasources.py`：数据源 API 按数据类型/provider 返回精确健康度，兼容旧注入替身。

- 测试：新增熔断/空数据不熔断覆盖；核心回归 43 passed，marketdata 全量 **217 passed**；`tsc -b` 与 `vite build` 通过。

**刻意边界**：健康状态仍是进程内内存（重启清空）；尚未将每次调用的 vendor/时间戳写入所有 Agent 原始输入。前者适合先观察实际阈值，后者应在东芯 dry-run 中按实际报告结构补充，避免无目的扩大 payload。

#### R2 纠偏记录（2026-07-29，全量审计发现，待所有者审计确认）

审计发现 R2 实施与本计划的两处偏差，已于当日修复（明细见 docs/30 §7）：

1. **熔断阈值硬编码 → 可配置**：`InMemoryMetricsSink(circuit_failure_threshold=, circuit_cooldown_sec=)` 构造参数 > 环境变量 `MARKETDATA_CIRCUIT_FAILURE_THRESHOLD` / `MARKETDATA_CIRCUIT_COOLDOWN_SEC` > 默认 3 次/300 秒，落实本节「阈值和时长不写死在业务逻辑中」。
2. **错误分类落地**：新增 `ConfigError`（token 缺失/鉴权/依赖未安装），Engine 按 config / transport / empty 三类下传 `error_class`；config 单列计数不熔断，transport 计入熔断；`tushare` vendor 缺包/缺 token 改抛 ConfigError、`pro.daily` 传输异常不再吞成 `[]`（此前该源永远无法熔断且分类失真）。
3. 顺带修复审计发现的 P0：`server.py` SPA 静态路由路径穿越（未授权可下载 `data/panwatch.db`），realpath 前缀校验 + 4 例回归测试。
4. 测试基线：主套件 833 passed、marketdata 221 passed。

### R3 · 东芯 10 个交易日保真验证

**启动前置条件**：R1 已发布且 Tushare 实测结论明确；R2 的关键数据闸门已上线；管理员已在 UI 完成 AI 服务、东芯 7 条正式触发器和 3 个定时 Agent 的配置。

**执行方式**：

- 第 0 日 dry-run：不发送真实通知，验证 10:00、14:45、18:00 三条链路、档案/流水注入、触发器与失败原因落库。
- 连续 10 个交易日双跑：每日填写固定表单，核对价格/换手/资金流、触发器状态、简报契约、决策倾向、发送延迟和数据来源。
- 偏差分级：机械数据/触发器错误为阻断；契约失败为高优先级修复；主观策略差异进入复盘，不在对照期内频繁改提示词。
- 期末输出一份结论报告，明确“推广 / 修正后再跑 / 停用”之一。

**通过标准（建议）**：机械触发器 100% 可解释且无未解释错漏；早晚简报契约合格率 ≥95%；每次抑制/降级都有记录；数据源与人工抽查的差异逐项裁决。

**决策 D29-3**：✅ 已确认（2026-07-27）：采用上述通过标准，由所有者最终人工裁决。

### R4 · 发布与回滚流程产品化

**目标**：不再依赖记忆或手工拼命令完成一次安全发布。

**拟改动**：

- 调查并修正 tag push 未触发 GitHub Actions 的原因；为手动触发增加等价且可追溯的 tag/ref 校验，避免“从 main 构建、却声称是某 tag”的歧义。
- 新增发布脚本/Make 目标：检查工作树、版本格式、测试、tag 指向、镜像 manifest、部署前快照和部署后健康检查。
- 新增 NAS 部署脚本或受版本控制的 runbook：备份 compose、固定指定 tag、`compose pull/up`、等待 healthy、核验 `/api/health` 与 `/app/VERSION`。
- 新增回滚命令：恢复上一份 compose 备份及指定镜像 tag，完成同样的版本/健康验证；对数据库迁移版本强制要求演练说明。
- 形成发布记录模板，保存 CI URL、镜像 digest、NAS 前后版本、验证结果和回滚点。

**验收**：以一个无破坏性版本进行“发布→验证→回滚→再发布”演练；tag 和镜像/运行版本一一对应；失败时不切换 NAS 容器。

**决策 D29-4**：✅ 已确认（2026-07-27）：固定版本并仅由发布流程切换；不自动跨版本升级。

### R0（不实施）· Mac 侧代理隧道守护

**最小方案**：只新增 Mac 用户级 LaunchAgent 与守护脚本。它每分钟经既有 `ssh nas` 检查 NAS 的 `7897` 本地监听与到 Mac Clash 的可达性；失效时在 NAS 远程启动原有的 `ssh -N -L …` 隧道。它不改 NAS 的网络设置、DNS、路由、防火墙或 Docker 网络。

**边界**：Mac 关机、Clash 未启动或 NAS 完全失联时仍无法代理；这是“自动恢复现有方案”，不是消除 Mac 单点。若以后需要真正去单点，再单开 NAS 原生代理/出口专项。

**验收**：手工停止隧道或重启 NAS 后，在 Mac 在线的情况下 2 分钟内自动恢复；失败时写本机日志并可选发通知。

**决策 D29-5**：⏭️ 已明确忽略（2026-07-27）。Mac 上的现有软件负责该渠道的恢复；本项目不新增 LaunchAgent 或相关运维脚本。
