# 28 · 后续改进路线图：从稳定性到产品闭环

> 日期：2026-07-27 ｜ 状态：**规划草案，等待所有者逐阶段确认**
>
> 本文是当前后续工作的排序依据；不替代 `docs/12`（持仓/方案功能）、`docs/17`（多租户）和 `docs/15-NAS部署与DevOps工作流计划.md`（部署）。三份既有计划已经实施的内容不重复排期。

## 1. 现状结论

项目已不是原始 PanWatch：持仓交易、方案档案、三时点跟踪、研究报告归档，以及 MT-P0～P5 多租户隔离均已有实现和自动化测试。当前应把目标从“继续堆叠功能”切换为：**先把真实 NAS 环境的可用性、可观测性与数据质量做成闭环，再用真实交易日验证 AI 跟踪的有效性，最后才扩展产品能力。**

### 已知事实与约束

| 领域 | 当前事实 | 规划含义 |
|---|---|---|
| 运行稳定性 | 0.4.2 修复了 DBLogHandler 持锁导致的 API 冻结；0.4.3 已把告警通知移出写事务、降低模拟盘扫描期间写锁竞争。 | 下个动作应先验证修复已发布并持续有效，不应立即扩功能。 |
| 数据源 | NAS 出口被东财接口限流/拒绝，12 个东财源应继续禁用；Tushare K 线已恢复代码但未以真实 token 取数验证。 | 需要建立“数据源可用性”治理，而不是只靠固定优先级。 |
| 网络依赖 | NAS 当前经 SSH 隧道使用 Mac 上代理；NAS 重启后隧道会丢失。 | 这是单点运行风险，必须自动恢复并监控。 |
| 业务闭环 | 东芯已导入方案和持仓；早盘/尾盘/收盘 Agent 仍需要真实 AI 凭据、正式规则和 10 个交易日对照。 | AI 输出质量尚未完成实盘验收，不能据此继续泛化到更多股票。 |
| 架构 | 多租户已完成，但 SQLite 单文件仍适合小规模自用，不适合不受控的高并发 SaaS。 | 本路线默认维持“小团队/家庭共享”的产品定位；规模变化时另立数据库与部署专项。 |

## 2. 优先级原则

1. **P0 先止损**：会令服务不可用、数据丢失或误导交易判断的问题，优先于体验与新功能。
2. **先量化后优化**：每项稳定性工作必须留下指标、告警阈值和回归用例，避免以主观“感觉变快”验收。
3. **行情真实性高于模型复杂度**：来源失效、延迟或口径不明时，宁可降级/不推送，不能让 LLM 对失真的输入包装成确定结论。
4. **先单股票验证，再多股票推广**：东芯的 D11 平行对照通过前，不扩展方案 Agent 的适用范围。
5. **阶段门禁不变**：每阶段先确认本阶段决策点，再改代码；完成后提交变更清单、自动化结果和人工验收记录，确认后进入下一阶段。

## 3. 推荐阶段与顺序

### P0 · 生产运行基线与遗留闭环（最高优先级）

**目标**：确认 0.4.3 的修复真正运行在 NAS 上，建立可复现的生产基线。

**范围**：

- 发布当前已验证代码并记录版本、镜像 digest、NAS 容器状态与健康检查结果；检查 tag push 未触发 release 的原因，修复后以一次 tag 发布验证。
- 连续采样 API 延迟、SQLite `database is locked` 日志、调度周期耗时、数据源失败率；确定正常基线和告警阈值。
- 将 SSH 代理隧道改为 NAS 可管理的自启动服务/计划任务，并提供失败后自动重连与状态探针；敏感凭据仍只保留在 NAS 配置中。
- 将东财源“禁用原因、替代数据源、恢复判定”写入运行手册；不因偶发成功重新启用。
- 对 NAS 数据卷执行一次可恢复备份演练（含 SQLite WAL 一致性校验），验证恢复副本可启动、可登录、持仓与方案数据可读。

**验收**：连续 5 个交易日内健康检查稳定；核心 API p95 延迟和锁错误率有记录且符合阈值；重启 NAS 后代理自动可用；备份恢复演练成功。

**决策点**：D28-1 是否允许通过 NAS 执行发布、重启、计划任务与备份演练；D28-2 发布策略是继续 Watchtower 追 `latest`，还是改为“指定版本 tag + 人工确认升级”。推荐后者，至少在迁移/数据源变更期采用。

### P1 · 数据源韧性与可观测性

**目标**：让系统能说明“本次结论用了什么数据、数据是否新鲜、源失效时如何降级”。

**范围**：

- 在现有数据源健康检查之上记录每个 `type/provider` 的成功率、延迟、最近成功时间、错误分类和连续失败次数。
- 为行情/K 线设置有限的熔断与恢复探测：连续失败的源暂时跳过，按冷却时间小流量探测恢复；不得把单次网络失败永久禁用。
- 在 Agent 原始输入与分析历史中记录数据来源和时间戳；数据过期或回退时加醒目提示，并对交易型简报选择降级或不推送。
- 配置并实测 Tushare token（仅 K 线），与现有替代源对 600519、688110 等样本比对日期、复权/成交额口径；明确其是否进入正式优先级。

**验收**：模拟一个上游源超时后，业务请求在设定时限内切到备源；UI/日志可追溯数据血缘；至少两周数据源健康报表；Tushare 的真实取数结论已签字。

**决策点**：D28-3 Tushare 是否作为 NAS 的正式 K 线主/备源（取决于 token 额度与实测稳定性）；D28-4 数据过期时，早晚简报选择“带降级标识推送”还是“直接抑制”。推荐：交易建议类直接抑制，资讯类可降级推送。

### P2 · Agent 实盘保真与操作纪律验证

**目标**：证明方案驱动的简报对真实持仓有帮助，而非只证明它能生成文字。

**范围**：

- 完成 AI 服务凭据、东芯正式触发器、Agent 绑定及 10:00 / 14:45 / 18:00 调度配置；先进行 dry-run，再开启通知。
- 执行 docs/12 的 D11：连续 10 个交易日与人工/Kimi 记录对照，检查行情准确性、触发器一致性、契约完整性和决策倾向。
- 将“无有效行情、契约失败、数据源降级、LLM 超时”统一标为明确失败原因，保留原始输入/输出以便复盘。
- 对发现的偏差只做小范围修正：优先改数据口径、触发条件和提示词契约；不在对照期内引入新的 Agent 类型或大模型框架。

**验收**：10 个交易日对照报告完成；机械触发器零漏报/误报或每一处有明确原因；简报契约合格率、延迟、人工可执行评分均可量化；所有偏差有处置结论。

**决策点**：D28-5 人工对照的最终裁决人及“通过”阈值；推荐设为：数据/触发器准确率 100%，简报契约合格率 ≥95%，其余语义差异逐项复盘而非硬凑一致。

### P3 · 运营安全与发布治理

**目标**：让升级、回滚、凭据和恢复可日常执行，而不依赖某次人工记忆。

**范围**：

- 形成版本发布清单：迁移影响、真实库副本演练、测试、镜像、部署后探针、回滚版本、变更通知。
- 增加备份保留与恢复演练周期，覆盖数据库、报告附件、配置；备份加密与访问权限单独核对。
- 将配置/密钥轮换、管理员邀请与禁用、报告签名链接有效期纳入定期自检。
- 补齐高价值端到端测试：双租户隔离、调度扇出、通知去重、数据源切换、备份恢复后的启动。

**验收**：一次预演从指定 tag 升级并回滚成功；恢复时间和数据恢复点目标（RTO/RPO）被记录；发布检查单可由非开发者按步骤完成。

**决策点**：D28-6 可接受的 RPO/RTO，以及是否将数据库从 SQLite 迁至 Postgres。推荐当前不迁移：先以演练和备份满足小规模场景；当并发用户、写锁或容量指标连续超阈值时另开迁移项目。

### P4 · 产品扩展（仅在 P0～P2 通过后立项）

**候选方向，需重新排序，不在本轮自动开工**：

| 候选 | 价值 | 前置条件 |
|---|---|---|
| 多股票方案模板与批量运营 | 将已验证的东芯流程推广到其他持仓 | P2 平行对照通过，定义通用模板与风险边界 |
| 回测接入真实行情与成本/涨跌停约束 | 用历史数据校验策略信号 | P1 数据口径确认；补足当前回测内核的涨跌停约束 |
| 组合级风险与再平衡 | 从单票提醒提升到资产配置决策 | 多账户/基准数据稳定、明确风险指标与授权边界 |
| 移动端推送体验与报告中心 | 提升日常可用性 | 通知可靠性和签名下载链路稳定 |
| 外部数据/券商导入 | 降低手工录入成本 | 安全评审、导入幂等性和对账机制 |

## 4. 不建议现在做的事

- 因多租户已完成就直接面向公开 SaaS 扩张；SQLite、代理和单实例调度仍是小规模部署设计。
- 在东财封锁尚未解除时反复启用东财源或堆叠更多同源 collector。
- 在 P2 对照期前追加更多 Agent、提示词花样或复杂策略；这会破坏归因。
- 以“测试全绿”取代 NAS 真实数据、重启恢复和交易日验证。

## 5. 建议的下一步

建议所有者先只确认 **P0 的两个决策点（D28-1、D28-2）**。确认后将本文件的 P0 拆成可审计施工计划，明确 NAS 操作窗口、备份目标、阈值和回滚命令；P0 验收后再进入 P1。
